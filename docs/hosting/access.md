# Invited access

Use separate Clerk development and production instances. In the Clerk dashboard, enable restricted (invitation-only) signup, email addresses and email verification codes; disable passwords, phone/social authentication and email links if they are enabled. Invite users through the Users dashboard. After an invited user accepts, open that user’s metadata editor and set private metadata `{"baseball_access": true}`. Only this owner-controlled flag authorizes questions; public/unsafe metadata and browser-supplied email addresses do not. This extra dashboard step keeps access closed even if signup settings are accidentally relaxed. These settings belong to the owner-managed Clerk application, not a browser-supplied approved-email list.

For removal, remove/set false the private approval flag or delete the existing user in the Users dashboard and revoke any outstanding invitation for that address. Revoking an invitation alone does not remove an existing account. Each question verifies the signed token's exact issuer and authorized origin, then checks its current session and user through Clerk's Backend API. A deleted user or revoked session is denied on the next request; an already running request may finish within its deadline. Do not use the paid Allowlist or ban features.

Production requires the live instance's public key, secret key, issuer and exact HTTPS application origin. Previews use a separate development instance and exact preview origin. Never share a production state database or live authentication instance with previews. Configure the production application's domain and email-code settings before publishing; test actual email delivery and account removal on the custom domain during provisioning.

Server secrets are entered through private Vercel environment settings or hidden CLI input. Only the publishable key, issuer and environment label reach the browser. Sign-out clears the displayed answer and pending clarification controls.
